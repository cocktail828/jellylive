1. 最高优先级：交付包未开启代码与资源裁剪
- scripts/build-container.sh:65 固定执行 :app:assembleDebug。
- 已合并的 Debug Manifest 确认 android:debuggable=true。
- app/build.gradle.kts:89 的 Release 也明确 isMinifyEnabled=false；未启用
  isShrinkResources，项目没有自定义 ProGuard 规则。因此仅切到 Release 不够。
- 当前依赖中的未用 API、序列化模型和旧页面仍进入 DEX；原始 DEX 总计
  55,568,064 字节，压缩后 21,493,743 字节，是优化的主要对象。
- 应先建立经过验证的压缩交付构建，启用 R8 和资源裁剪。项目 AGP 为 8.11.1，
  使用这一版本支持的 isMinifyEnabled/isShrinkResources/proguardFiles 配置；
  不应直接套用新版 AGP 的 optimization DSL。
- 保持当前 applicationId、签名和版本兼容。Debug 当前使用 .bestvlive 后缀，
  直接改执行 assembleRelease 会改变包名；不能把换任务名当作完整方案。

2. 大量旧 UI 与当前主流程并存，不能整片目录直接删
- app 主源码有当前 bestv 包 38 个文件、其余上游文件 420 个。
- DEX 中 bestv 包 604 个类，上游 androidtv 其余包 2500 个类；数字含生成类，
  不是可删除清单，也不能按类数直接换算压缩后体积。
- AndroidManifest 仍注册旧 StartupActivity、MainActivity、PreferencesActivity、
  ExternalPlayerActivity、屏保和系统内容入口，相关旧页面不是编译器可直接
  判定不可达的普通文件。旧 StartupActivity 还保留 SEARCH/VIEW 外部入口。
- 当前 LiveActivity 直接打开 JellyLibraryActivity，而非旧主页。新媒体播放器
  自建 ExoPlayer，旧 UI 的播放器、设置和导航框架仍被保留。
- 认证会话、服务器存储、图片加载、PlaybackManager 播放协商、设备能力描述、
  ReportingHelper 仍被新界面实际复用，不能连同旧 UI 删除。
- KoinInitializer 仍加载完整 appModule/playbackModule；模块中注册了旧导航、
  页面模型和播放器。后续须先拆分当前必需依赖，再收缩旧入口和资源。

3. 可明确调整的工具依赖
- gradle/libs.versions.toml:67 定义完整 androidx.compose.ui:ui-tooling，
  :136 将它放入 androidx-compose bundle；app 以 implementation 引用 bundle，
  因而不只 Debug 构建会带入完整预览工具。
- 实际 DEX 包含 androidx.compose.ui.tooling 下 164 个类，含 tooling.data 17 个。
  当前源码仅见旧 fadingEdges.kt 使用 @Preview，当前 bestv 页面没有 Compose UI。
- 完整预览运行工具应限定到开发构建；主源码的 @Preview 编译依赖需单独保留。
  Compose 全部 8165 个类中还包含旧 UI 的实际运行框架，不能将它们一概视为工具。

4. APK 内存在明显空洞
- 根据中央目录列出的本地条目偏移、实际本地头和压缩长度计算，相邻有效条目
  之间共有 2,819,836 字节间隙。数据描述符和正常对齐也包含在这个数字内。
- 最大一个间隙 2,344,312 字节，其中 2,343,952 字节为零；其余几个大间隙也
  几乎全零。未发现这些大间隙里存在有效的旧 ZIP 本地条目。
- 这与增量打包留下的空洞相符，属于原因推断。建议干净重建打包后比较；
  不能把所有 ZIP/签名开销都当作可删除内容，也未宣称已实测减小 2.8 MB。
- ZipFile.testzip() 完整 CRC 检查通过，未发现损坏条目。

5. 通用包同时携带四种架构
armeabi-v7a      755,562 字节
arm64-v8a       764,286 字节
x86             783,977 字节
x86_64          788,699 字节
- 都是 libffmpegJNI.so 与 libandroidx.graphics.path.so。
- 保留 ARM 两种架构时，x86 两种库的现存压缩条目合计 1,572,676 字节。
  如只保留 arm64，其余三种条目合计 2,328,238 字节；最终签名包差值需重建测量。
- 应按设备实际 ABI 分发，不能依据 4K 分辨率或芯片为 64 位推断系统 ABI。
  模拟环境仍可单独保留所需架构的构建。
- FFmpeg 扩展仍被当前两个播放器启用，不应仅为瘦身删掉现有音频兼容链。

6. 小范围未使用代码与重复逻辑
- LiveActivity.java 中 previewBorder():254、releaseJellyfinPlayback():676、
  languageLabel():864、nextProgram():886：扫描全部生产源码、XML 和仓库检查
  脚本，方法名仅在定义出现，未找到调用。属于可清理的旧辅助方法候选。
- JellyLiveBridge.loadChannels():64 没有调用；searchMedia():71 也没有外部调用，
  后者只连接 LibraryRepository.searchMedia() 这条旧搜索链。
  当前媒体搜索在 JellyLibraryActivity:815 通过 LibraryBrowse.search(catalog)
  实现；删除旧搜索链不能误删这个实际入口。
- LibraryConnections.readPreset() 与 JellyLibraryActivity.restoreInitialConnection()
  分别复制读取、限长、解析和校验 jellyfin-bootstrap.json 的流程，适合共用加载器。
- 切换库时 verifyAndActivate() 先以隔离客户端 getCurrentUser，再调用
  switchCurrentSession()，后者 setCurrentSession() 又验证一次用户。此处有合并
  验证的空间，但必须保留成功才切换、取消不覆盖原会话的约束；本轮只确认
  静态调用链，未测量请求时序或认定为运行故障。
- 这些小方法和重复逻辑的清理主要降低维护成本，不能解决数十 MB 包体问题。

建议实施顺序
1) 保持 UI、包名、签名与数据兼容，做干净打包并实测空洞差异。
2) 建立 R8/资源裁剪交付构建，把预览工具限制到开发构建。
3) 分离当前需要的认证/协商/图片链与旧页面，逐项删除旧入口及其专属资源。
4) 根据目标设备 ABI 生成对应产物，保留通用包或模拟器包按需使用。
5) 清理上述无调用方法，统一配置加载和重复校验。

验证边界
- 减包后的功能、4K 焦点、序列化、反射调用和播放兼容性均未在本轮验证。
- 没有对所有旧 UI 或第三方库做完整方法级可达性分析，不承诺具体最小包体。
- 资源表与 res/ 合计 3,769,753 字节是现存总量，并非全部可删。
